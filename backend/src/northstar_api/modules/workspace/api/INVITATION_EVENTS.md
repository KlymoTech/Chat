# Workspace invitation lifecycle — additive audit and event contract

Existing HTTP APIs remain unchanged: `POST /api/v1/workspace/invitations`, `POST /api/v1/workspace/invitations/{id}/resend`, `DELETE /api/v1/workspace/invitations/{id}`, and public `/api/v1/workspace-invitations/{preview,accept,signup,decline}`. The existing `/v1` alias, validation, token rotation, permissions, rate limiting, and delivery pipeline stay in place. Do not add duplicate routes or delete legacy services.

`modules/workspace/services/invitation_audit.py` stages one `IntegrationAuditEvent` and one `OutboxEvent` in the **same database transaction** as each persisted invitation transition. Audit action names are `workspace.invitation.invited`, `.resent`, `.revoked`, `.accepted`, `.declined`, `.delivery_succeeded` and `.delivery_failed`; outbox event types append `.v1`. Outbox aggregate type is `workspace_invitation`, aggregate ID is the invitation UUID, and each event is scoped by `tenant_id` and `workspace_id`. The allowlisted payload is `{ "workspaceId": "UUID", "invitationId": "UUID", "role": "viewer", "allAgentsAccess": true }`, optionally with `agentCount` for issue/accept. **Never store raw invitation tokens, token hashes, email recipients, email links, password contents or delivery exception text** in these records.

The authenticated issuer/resender and accepting account are recorded as audit actors. The protected invitation router installs `capture_invitation_administrator`, which stores the verified principal and real HTTP request on the request-scoped SQLAlchemy session. `invitation_audit` resolves a missing actor **only for revocation and only for an exact tenant/workspace match**, preserving the existing DELETE signature without impersonating the original inviter. It passes the request to the existing audit recorder for request ID, IP and user-agent; neither request data nor the actor's credentials are copied into the outbox event. A missing/mismatched scope or invalid object fails closed. Public invitation routes do not install this dependency; decline remains anonymous. **Actual FastAPI/deployed PostgreSQL confirmation is still required.**

Revoking an already-`REVOKED` invitation returns the existing HTTP `204` after its tenant/workspace-scoped locking lookup, without rotating the token hash, changing timestamps, flushing a mutation or writing another `workspace.invitation.revoked` audit/outbox event. Accepted invitations retain their existing `409`; unknown or out-of-scope invitations retain `404`. A newly revoked invitation still rotates its token hash and stages exactly one event. The unit tests in `backend/tests/test_workspace_invitation_revocation_idempotency_unit.py` cover these states. The HTTP/database regression in `backend/tests/test_workspace_invitation_revocation_idempotency_api.py` additionally checks that repeated DELETE leaves token hash, timestamps and audit count unchanged; **that integration test is committed but not verified passing**.

These events are audit/outbox records; they do not themselves provision an email-delivery queue or guarantee that an already sent email rolls back when a later delivery-status commit fails. The current invitation route still sends SMTP synchronously after the invitation transaction. **Durable queued email delivery remains an acceptance gap.** The existing outbox publisher sends event envelopes to Kafka; an event with no invitation token cannot recreate an email link, so implementing a reliable queue requires a separately secured, durable token-delivery design rather than adding a plaintext token to audit/event payloads. Do not claim external delivery is transactionally atomic.

Public signup/accept and decline set the invitation tenant's database context before creating tenant-scoped audit/outbox records; existing principal authorization and invitation token validation remain authoritative. Only a valid invitation token can select the tenant in the public path. The tenant context has to be verified against actual PostgreSQL RLS using the runtime application role, not only SQLite.

Test sources: `backend/tests/test_workspace_invitation_audit_unit.py` (eight isolated cases), `backend/tests/test_workspace_invitation_revoker_actor_unit.py` (three isolated cases), `backend/tests/test_workspace_invitation_revocation_idempotency_unit.py` (four isolated cases), `backend/tests/test_workspace_invitation_audit_api.py`, `backend/tests/test_workspace_invitation_revoker_actor_api.py`, and `backend/tests/test_workspace_invitation_revocation_idempotency_api.py` (HTTP/database regressions). **Eleven prior invitation helper tests and four additional revocation unit tests passed in isolated stubbed fixtures; the API/database tests remain unverified.** Before promotion run full invitation tests, transaction rollback and wrong-tenant tests, full backend/frontend suites, lint/format/mypy/typecheck, PostgreSQL migrations, and GitHub CI. Do not merge the draft Workspace PR on the strength of isolated helper tests.

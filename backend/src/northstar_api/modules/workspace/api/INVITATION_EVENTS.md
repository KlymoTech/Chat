# Workspace invitation lifecycle — additive audit and event contract

Existing HTTP APIs remain unchanged: `POST /api/v1/workspace/invitations`, `POST /api/v1/workspace/invitations/{id}/resend`, `DELETE /api/v1/workspace/invitations/{id}`, and public `/api/v1/workspace-invitations/{preview,accept,signup,decline}`. The existing `/v1` alias, validation, token rotation, permissions, rate limiting, and delivery pipeline stay in place. Do not add duplicate routes or delete legacy services.

`modules/workspace/services/invitation_audit.py` stages one `IntegrationAuditEvent` and one `OutboxEvent` in the **same database transaction** as each persisted invitation transition. Audit action names are `workspace.invitation.invited`, `.resent`, `.revoked`, `.accepted`, `.declined`, `.delivery_succeeded` and `.delivery_failed`; outbox event types append `.v1`. Outbox aggregate type is `workspace_invitation`, aggregate ID is the invitation UUID, and each event is scoped by `tenant_id` and `workspace_id`. The allowlisted payload is `{ "workspaceId": "UUID", "invitationId": "UUID", "role": "viewer", "allAgentsAccess": true }`, optionally with `agentCount` for issue/accept. **Never store raw invitation tokens, token hashes, email recipients, email links, password contents or delivery exception text** in these records.

The authenticated issuer/resender and accepting account are recorded as the audit actor. The protected invitation router now installs `capture_invitation_administrator`, which stores the already-verified principal on the request-scoped SQLAlchemy session; `invitation_audit` uses that actor **only** when the legacy revocation service does not supply one and both tenant and Workspace match. This preserves the existing DELETE signature and avoids attributing the action to the earlier inviter. Public invitation routes do **not** install that dependency: decline and transport delivery events remain anonymous. No identity is taken from headers or request bodies. The helper fails closed to a null actor if its authenticated scope or UUID type is absent. A full HTTP/DB test must still confirm FastAPI dependency injection and persisted attribution.

These events are audit/outbox records; they do not themselves provision an email-delivery queue or guarantee that an already sent email rolls back when a later delivery-status commit fails. The current invitation route still sends SMTP synchronously after the invitation transaction. **Durable queued email delivery and complete request IP/user-agent attribution remain acceptance gaps.** Do not claim external delivery is transactionally atomic. The existing outbox publisher sends event envelopes to Kafka; an event with no invitation token cannot recreate an email link, so implementing a reliable queue requires a separately secured, durable token-delivery design rather than adding a plaintext token to audit/event payloads.

Public signup/accept and decline set the invitation tenant's database context before creating tenant-scoped audit/outbox records; existing principal authorization and invitation token validation remain authoritative. Only a valid invitation token can select the tenant in the public path. The tenant context has to be verified against actual PostgreSQL RLS using the runtime application role, not only SQLite.

Test sources: `backend/tests/test_workspace_invitation_audit_unit.py` (eight isolated cases), `backend/tests/test_workspace_invitation_revoker_actor_unit.py` (three isolated cases), `backend/tests/test_workspace_invitation_audit_api.py` and `backend/tests/test_workspace_invitation_revoker_actor_api.py` (HTTP/database regressions). **Eleven focused invitation helper tests pass in a stubbed fixture; the API/database tests remain unverified.** Before promotion run full invitation tests, transaction rollback and wrong-tenant tests, full backend/frontend suites, lint/format/mypy/typecheck, PostgreSQL migrations, and GitHub CI. Do not merge the draft Workspace PR on the strength of isolated helper tests.

# Removing a disabled Workspace member

The permission-protected `GET /api/v1/workspace/members/details` includes existing memberships for globally disabled users and labels them `disabled`. This is separate from `active`/`suspended` Workspace membership lifecycle: the member's **global account remains disabled** and is not authorized to use the Workspace.

In the Workspace Members details panel, users with the existing `members.manage` permission can choose **Remove disabled member**, review the member's name and email and type `REMOVE` to confirm. The action calls the existing `DELETE /api/v1/workspace/members/{user_id}` with the current authenticated tenant and `X-Workspace-ID`; it does not introduce a new privileged endpoint. The backend retains all existing owner and last-available-administrator protections, scoped audit/outbox, and the no-global-account-deletion contract. A denied API request leaves the confirmation dialog open with a visible error. Successful deletion emits the existing member-changed event and reloads Workspace-scoped details; other member controls remain unchanged. Users without `members.manage` see no cleanup action.

Regression sources: `frontend/src/features/workspace/members/WorkspaceMemberDetailsPanel.disabled-removal.test.tsx` covers permission hiding, active-account exclusion, typed confirmation, successful refresh and denial/error states. `backend/tests/test_workspace_disabled_member_removal_api.py` covers disabling an invited viewer, confirming the scoped details status, deleting the existing membership while disabled, and verifying the global user row survives. Existing disabled visibility and last-admin tests still apply. These new tests are committed, **not verified passing** in a complete application/DB/frontend environment. Existing CI, PostgreSQL RLS and migration acceptance must pass before Members/Invitations or sections 22–44 can be considered complete. No old route, feature or file is removed.

## Reactivating a Workspace member whose global account is disabled

The existing `POST /api/v1/workspace/members/{user_id}/reactivate` now checks the global `User.is_active` state inside its member-lifecycle transaction, after validating the selected tenant/workspace membership and before altering suspension state or staging audit/outbox. It returns `409` for a globally disabled account rather than incorrectly claiming that Workspace access has been restored. This endpoint **does not** enable a global account. Account restoration is a separate authorized operation outside Workspace management; only after that operation succeeds may an authorized Workspace administrator retry reactivation. Existing owner/last-admin safeguards and normal active-account suspension/reactivation remain in place.

Regression: `backend/tests/test_workspace_disabled_member_reactivation_api.py` covers a disabled suspended member receiving `409` with suspension retained and a successful reactivation following authorized account restoration. This test is committed but not verified in the complete application, PostgreSQL, or CI environment. This guard must not be interpreted as acceptance of the entire Members/Invitations capability.

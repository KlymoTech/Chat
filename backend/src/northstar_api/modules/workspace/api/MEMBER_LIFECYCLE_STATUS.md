# Workspace member lifecycle status

`GET /api/v1/workspace/members/lifecycle` requires the existing authenticated tenant, selected `X-Workspace-ID` and `members.view` permission. It returns the current members of **that tenant and workspace**. Its `status` is `active`, `suspended` or `disabled`: a globally disabled user is always `disabled`, even when its Workspace suspension row is present or absent. The projection joins global account state through the exact scoped membership and does not modify or delete either record. This matches `GET /api/v1/workspace/members/details`.

`POST /api/v1/workspace/members/{user_id}/reactivate` remains Workspace-only: with the existing `members.manage` permission, an interactive session, a reason and typed confirmation, it may clear Workspace suspension only for an active global account. A disabled global account receives a controlled `409` before any lifecycle state, audit or event mutation. The frontend does not offer Reactivate for a `disabled` status; it preserves Reactivate for a suspended, globally enabled member. Disabled member cleanup remains a separately confirmed removal through the pre-existing guarded DELETE endpoint, not global user deletion.

**Lifecycle UI reconciliation:** The pre-existing `/workspace/members` access-editor API intentionally lists only globally active accounts. The lifecycle UI also reads the already permission-protected `/workspace/members/details` projection, adds any missing members by user ID and takes status from `/workspace/members/lifecycle`. It never fabricates resource scopes for these additional rows or adds them to the legacy access editor. A globally disabled member therefore stays visible as `disabled` without an inappropriate Reactivate or Suspend action. The Workspace transition response may still be `disabled` after a successful suspension; the frontend emits the requested `member-suspended` event rather than misreporting a reactivation. Existing Workspace selection and account-change guards remain in the API client.

**Account state is not Workspace access state:** The legacy access editor labels its globally enabled membership rows `Account enabled` under `Account-enabled members`, rather than asserting they have `Active` Workspace access. An enabled account can still be suspended in a Workspace; the separate Member lifecycle panel shows the actual `active`, `suspended` or `disabled` status. The existing role/agent access editor and its API contracts are unchanged by this display correction.

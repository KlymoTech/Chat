# Workspace invitation email — encrypted durable delivery (incremental)

**Scope:** Workspace invitations only. Existing authentication, invite/accept/decline/resend/revoke contracts and other channels remain unchanged. This capability is **not accepted or production-ready** until migration, PostgreSQL RLS, actual SMTP/broker delivery, rollback/retry, security and full repository CI pass. Draft PR #129 must not be merged prematurely.

## Activation and safety

1. Apply additive migration `0057_workspace_invitation_email_jobs` (after `0056_workspace_member_invitation_origin`), and verify tenant RLS under the actual `northstar_app` runtime role before enabling delivery.
2. Generate a **separate** Fernet key securely, for example locally: `python -c 'from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())'`. Store it in the existing secrets manager as `WORKSPACE_INVITATION_DELIVERY_KEY`. Never commit it, log it or reuse `JWT_SECRET`, MFA, CRM or WhatsApp keys. API and Celery worker processes must use compatible keys; the dispatcher publishes opaque identifiers only and does not need the decryption key. Protect DB backups because pending-job ciphertext remains decryptable with the key.
3. Set `EMAIL_DELIVERY_MODE=smtp` and configure `SMTP_HOST` and other required SMTP values using existing `EmailSettings`. Set `BACKGROUND_DISPATCH_ENABLED=true` and run the existing `northstar-job-dispatcher` and `northstar-worker` processes with the existing durable RabbitMQ broker. Ensure the worker consumes `workspace.email` and that the `workspace.email.failed` dead-letter queue is monitored. Do not enable a production/staging invitation route without migration, matching worker configuration and valid mail credentials.
4. Production/staging invitation creation and resend **fail closed (503)** if the separate key, enabled dispatcher or SMTP mode is missing. Development/test without the new key retain their existing synchronous email behavior for compatibility; development/test with the key use the new queue and require SMTP mode.

**Compose topology:** Default `docker compose` automatically merges the existing `compose.yaml` and `compose.override.yaml`. The override now adds `workspace.email` to the existing `worker` subscription **without dropping** `ingest.source`, `operations`, `telegram.outbound`, `instagram.outbound`, `facebook_messenger.outbound` or `slack.outbound`; the separate `whatsapp-worker` subscription stays unchanged. It also forwards the key ring, `EMAIL_DELIVERY_MODE`, sender details and SMTP configuration to the API and worker from environment variables or the local `.env` file. Supply real values through the deployment secret manager; no real keys are committed. If deployment commands explicitly use `-f compose.yaml`, also include `-f compose.override.yaml`, otherwise they bypass this existing override and the Workspace worker subscription. Avoid publishing `docker compose config` output or container environment dumps containing SMTP credentials or the key ring. The dispatcher needs no invitation decryption key. Kubernetes `northstar-worker` has no explicit `--queues` filter and reads its mail settings through the existing ConfigMap/Secret references; provision the independent Fernet key in `northstar-secrets` before activation. Do not assume that a configured queue proves a live worker is consuming it: verify `workspace.email` is subscribed and an invite is delivered in a controlled SMTP sink.

## Workflow and storage

`POST /api/v1/workspace/invitations` and `/invitations/{id}/resend` use the existing authorization, validation, token creation and invitation audit/outbox. Before committing, they encrypt the newly issued raw invite token with Fernet into `workspace_invitation_email_jobs` in the **same** transaction. The response reports `deliveryState: not-sent` until a worker confirms SMTP delivery. The ordinary audit/Kafka outbox never receives recipient email, token, token hash, invitation URL or ciphertext; the RabbitMQ task contains only tenant ID and opaque email-job ID.

Before publishing tasks, the existing job dispatcher cancels and scrubs **queued/failed** encrypted jobs if their invitation was revoked, accepted, expired or superseded, if the job's tenant/workspace does not match the invitation, **or if the matching workspace is archived**. The SQL existence check verifies both the workspace ID and its tenant ID; an archived workspace is not deliverable and cannot keep retrying a pending credential. This SQL cleanup runs in the dispatcher's existing DB transaction without waiting for an SMTP worker; it does **not** claim instantaneous scrubbing at the moment an invitation or workspace changes. Sent/terminal jobs and valid jobs are untouched. The Celery worker independently rechecks same tenant/workspace, active workspace, pending status, expiration and exact current token hash, decrypts only inside the worker and calls the existing SMTP sender. It records secret-free delivery audit/outbox and purges ciphertext on success or terminal cancellation/failure. Existing invitations' transitions retain their own audit records; internal cleanup does not issue duplicate invite events. Verify dispatcher operation and retention cleanup in production; paused dispatchers, offline workers and database backups may still retain ciphertext until recovery or backup expiry.

Broker dispatch has up to eight attempts and mail delivery has up to eight attempts with backoff. On terminal broker failure the job is marked `dispatch_failed` and ciphertext removed; a user can resend to generate a new credential and job. On terminal SMTP failure the job is marked `delivery_failed`, ciphertext removed and existing invitation `deliveryState` reports failure. The mail transport is **at least once**, not exactly once: a crash after SMTP accepted a message but before the transaction commits may generate a duplicate email. Never claim guaranteed exactly-once delivery.

## Key rotation for outstanding encrypted jobs

`WORKSPACE_INVITATION_DELIVERY_PREVIOUS_KEYS` is an optional **secret**, containing comma-separated prior Fernet keys, newest first. The primary `WORKSPACE_INVITATION_DELIVERY_KEY` always encrypts **new** jobs; the key ring decrypts older pending jobs. A prior key without a primary key, an invalid key, an empty entry, or a repeated key fails configuration closed without exposing key material. With only the primary key configured, the original single-key behavior remains.

For a coordinated rotation: generate a new independent key; configure the **workers first** with the new primary and the old key in `WORKSPACE_INVITATION_DELIVERY_PREVIOUS_KEYS`, keeping API issuers on the old key until those workers are ready. Then deploy API issuers with the new primary and previous old key; confirm all processes use the intended ring and test delivery of an existing queued job and a newly issued job against a controlled SMTP sink. Keep prior keys available until old ciphertext is delivered or purged and all older issuers have stopped. Remove previous keys only after checking pending, failed and delayed jobs **and backups/retention obligations**. If a worker is still running on an old-only key during rollout, it cannot decrypt a new-key job and can retry it; coordinate rollout to avoid exhausting delivery attempts. Do not log keys or ciphertext, and do not treat this rollout as validated without a real broker/PostgreSQL test.

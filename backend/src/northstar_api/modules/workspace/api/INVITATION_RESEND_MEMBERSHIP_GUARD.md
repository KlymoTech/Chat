# Workspace invitation resend and acceptance — current-membership safety

**Ownership:** Only Workspace-owned invitation behavior is affected. Legacy `/workspace/members` routes, public route paths and request schemas, WhatsApp, CRM and Super Admin are unchanged.

An invitation may remain pending after its recipient joins a Workspace through another administrative path. The additive `invitation_resend_membership_guard.py` performs an early read of the invitation email using the authenticated **tenant ID, selected Workspace ID and exact invitation ID**, then checks membership under that same tenant and Workspace. A known member receives **409** before HTTP resend proceeds. An unknown invitation remains subject to the existing 404; readers without `members.manage`, unrelated routes and malformed IDs do not perform the guard's invitation lookup.

**The service also rechecks:** `resend_workspace_invitation()` locks the active, matching Workspace and then the matching invitation, and rechecks the same tenant/workspace membership **after those locks and before rotating the credential, staging email or recording the transition**. `_accept_invitation()` now rejects a previously established Workspace membership with **409** instead of changing that member's newer role or selected-agent access. This applies to existing-account acceptance and keeps the existing signup path, routes and public response contracts. The owning API endpoints roll back on `WorkspaceInvitationError`. Neither path deletes existing membership data.

**Verification still required:** A membership added by an unrelated code path that does not observe the same locking order could still race the resend query. A unique-membership constraint and the acceptance rejection reduce impact but do not prove that duplicate mail is impossible; do not assert exactly-once delivery or fully tested serializability. Run actual PostgreSQL multi-session tests for membership creation vs. resend/acceptance, tenant isolation, migrations and rollback, plus complete FastAPI/SMTP/queue and frontend regressions before Members/Invitations can be accepted.

Regressions: `backend/tests/test_workspace_invitation_resend_membership_guard_unit.py` checks the request boundary and scoped predicates; `backend/tests/test_workspace_invitation_resend_workspace_guard_unit.py` checks lock/query ordering and successful non-member resend; `backend/tests/test_workspace_invitation_existing_member_safety_unit.py` checks service 409, unchanged token/status, preserved role and agent access, and no delivery/audit side effects.

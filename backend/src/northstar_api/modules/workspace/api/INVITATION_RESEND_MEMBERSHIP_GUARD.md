# Workspace invitation resend — current-membership safety

**Ownership:** Only the Workspace-owned protected invitation resend endpoint is affected. The legacy `/workspace/members` routes, public invitation acceptance/signup/decline, WhatsApp, CRM and Super Admin are unchanged.

An invitation may remain pending after its recipient joins a Workspace by another administrative path. Resending that invitation could create and email another credential whose acceptance service would update an existing member's role and agent access. The additive `invitation_resend_membership_guard.py` therefore reads the invitation email using the authenticated **tenant ID, selected Workspace ID and exact invitation ID**, then checks current membership using the same tenant and Workspace and a case-normalized user email. A known member receives **409** before token rotation, email staging or audit. An unknown invitation remains subject to the existing 404; readers without `members.manage`, unrelated routes and malformed IDs do not perform the guard's invitation lookup. This does not change the existing service, accepted-invitation behavior or public router.

**Not yet a complete race fix:** This HTTP preflight is read-only and does not hold the Workspace row lock. A membership created between the preflight and token rotation, or a previously issued invitation accepted after membership was created through another path, may still reach the existing service's update-of-existing-membership branch. A transactionally locked service-level membership check and matching public-acceptance safeguards need characterization, implementation and actual PostgreSQL concurrency tests before Members/Invitations can be accepted. Do not describe this preflight as complete protection.

Regression: `backend/tests/test_workspace_invitation_resend_membership_guard_unit.py` checks same-tenant/same-Workspace predicates, no write or audit side effects on rejected resends, normal non-member pass-through, and route/permission bypasses. An isolated, Git-blob-matched SQLAlchemy harness passed six cases; the committed test suite and real FastAPI/PostgreSQL flow remain unverified.

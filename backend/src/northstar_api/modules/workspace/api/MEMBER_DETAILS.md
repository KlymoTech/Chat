# Workspace member details (incremental)

`GET /api/v1/workspace/members/details` (and the existing `/v1` alias) uses bearer authentication, selected `X-Workspace-ID`, entitlement guard and `members.view` permission. It returns current membership records from the selected tenant **and** workspace, including disabled global accounts so administrators can diagnose unavailable members. The response is an array (`[]` when empty); an unauthorized or nonexistent selected workspace is denied by principal resolution. This endpoint does not enable disabled accounts or change legacy invitation/edit/removal routes.

Fields: `userId`, `name`, `email`, `role`, `status` (`active`, workspace `suspended`, or globally `disabled`), `mfaEnabled`, `lastLoginAt`, `invitedByUserId`, `joinedAt`. `disabled` takes precedence over `suspended` in this read-only view; authentication still rejects disabled users. `mfaEnabled` and `lastLoginAt` are **global-account** properties, not Workspace-specific MFA enforcement or last Workspace activity. `joinedAt` is the membership creation timestamp.

**Exact current-membership invitation provenance:** migration `0056_workspace_invitation_origin` creates `workspace_member_invitation_origins` with `tenant_id`, `(workspace_id, user_id)` membership key, and unique `invitation_id`. An `accepted` invitation transition stages that link in the same transaction as membership creation/update and the existing allowlisted audit/outbox; no invitation token, token hash, email, or link enters provenance or audit. A composite foreign key cascades the link on membership removal; original invitation/audit history is retained. The member-details projection resolves `invitedByUserId` **only through this link**, and rechecks the linked invitation's tenant, workspace, accepted status and accepted user. Existing memberships are deliberately **not backfilled by timestamps**: `invitedByUserId` is `null` without an exact link, including members joined before this migration or added directly. An inviter whose account has been deleted may also appear as `null` through the invitation's `ON DELETE SET NULL` foreign key. Historical timestamp helper code remains for compatibility but is not used to assert member provenance.

The endpoint does not fabricate teams, last Workspace activity or Workspace MFA policies. The Members screen preserves the existing invitation, edit, remove and agent-access controls, the lifecycle panel and the separate confirmed disabled-member removal action. Details support Refresh, loading, empty and retryable error states; workspace selection uses the existing context-safe API client.

Regression coverage: `backend/tests/test_workspace_member_invitation_origin_api.py` (acceptance writes exact link, correct scoped inviter and deletion), `backend/tests/test_workspace_invitation_audit_unit.py` (one link only for acceptance; no secret payload), existing member details/disabled member/API tests and frontend component tests. An isolated **Git-blob-matched model** passed four SQLite foreign-key/uniqueness/cascade assertions; the real HTTP/database tests, PostgreSQL migration/RLS/concurrency, frontend/browser tests and full CI are **not verified passing**. Deploy migration before the new API code. No preexisting tables, files or routes were deleted or replaced.

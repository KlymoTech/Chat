# Workspace active-administrator availability guard

The existing `POST /api/v1/workspace/members/{user_id}/suspend`, `PATCH /api/v1/workspace/members/{user_id}` and `DELETE /api/v1/workspace/members/{user_id}` endpoints retain their paths, permission dependencies and request contracts. An administrator cannot be suspended, demoted or removed if doing so would leave no other **usable** administrator. The explicit owner-transfer protection remains independent and must also succeed. No additional frontend bypass or role is introduced.

`services/admin_availability.py` counts administrator memberships in the exact `tenant_id` and `workspace_id`, joined to an active global `User` and a matching `TenantMembership`, excluding members suspended in `WorkspaceMemberState`. Disabled accounts, missing organization memberships, suspended administrators and administrators in other tenants/workspaces cannot satisfy this safeguard. For demotion and removal, the count explicitly **excludes the target member**, so a target cannot count as their own replacement. The suspension service counts the target and refuses a transition from active to suspended when that count is less than two. All checks are performed after the selected workspace is locked and before state updates or audit/outbox staging. An unchanged admin role, non-admin removal, reactivation and other existing operations retain their existing behavior. Repeated suspension remains a no-op unless another independent guard rejects it.

Member removal still deletes only the selected Workspace membership and its Workspace-scoped state; it does not disable the global account. These checks do not replace separately authorized Workspace owner recovery, nor prove a tenant is healthy if it was already left without a usable administrator by another subsystem.

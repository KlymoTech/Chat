# Workspace active-administrator availability guard

The existing `POST /api/v1/workspace/members/{user_id}/suspend` endpoint retains its path, permission dependencies, confirmation and reason contract. When suspending an administrator, it now refuses the transition with HTTP `409` if there is no **other available administrator**. There is no additional frontend switch or privileged bypass.

`services/admin_availability.py` counts administrator memberships in the exact `tenant_id` and `workspace_id`, joined to an active global `User` and matching `TenantMembership`, excluding any member with an active suspension in `WorkspaceMemberState`. A disabled account, missing organization membership, suspended workspace administrator or admin in another workspace/tenant cannot satisfy this safeguard. The service performs this check after locking the workspace and target member, after explicit owner protection, and **before** it updates the suspension row or stages audit/outbox events. Reactivation and suspension of non-admin roles do not require the count. A repeated already-suspended request remains the existing no-op.

This is an additive safeguard; legacy member/invitation routes and teammate-owned modules remain untouched. Existing role-edit and removal paths have an older last-admin count that does not yet exclude suspended accounts, so the same invariant must still be reconciled there before Members is declared complete. This safeguard is not a replacement for the independent explicit Workspace ownership/recovery rules.

Verification: isolated SQLAlchemy fixture ran ten focused unit cases with warnings treated as errors, including the existing lock-order tests; a separate SQLite fixture executed the actual count statement and verified suspended/disabled/org-orphan exclusion plus tenant/workspace scope.

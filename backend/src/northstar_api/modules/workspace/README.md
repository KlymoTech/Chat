# Workspace feature module — incremental migration

This directory owns new workspace capabilities without deleting or relocating existing implementation. The public API remains `GET/PATCH /api/v1/workspace` (with the existing `/v1` alias); authentication, workspace selection (`X-Workspace-ID`), permission enforcement, validation, legacy branding, security, members, invitations and API keys continue through the existing routers. This module is **not** a replacement workspace router yet.

## General settings — implemented code, acceptance pending

`services/general_settings.py` is called by `northstar_api.routers.workspace.update_workspace` after existing validation and before the existing database commit. It compares persisted `name`, `slug`, `timezone`, `default_language`, `date_format`, and extended preferences; it records only genuinely changed field names. It stages a `workspace.settings.updated` audit record (actor, tenant and workspace IDs) and a `workspace.settings.updated.v1` outbox record (tenant and workspace IDs) in the same transaction. On transaction failure, the workspace change, audit record and event roll back together. Outbox payload: `{ "workspaceId": "<UUID>", "fields": ["name", "timezone"] }`. **Old and new values, access tokens and secrets are not included.** Unchanged general settings do not produce a domain event. Legacy security and branding paths retain their pre-existing events and behavior.

The existing `GET /api/v1/workspace` response and `PATCH /api/v1/workspace` request/response schemas remain compatible. `WorkspacePreferences` extends its original timezone, language and date format with industry, country, description, time format, three-letter currency, week start, workspace icon and validated seven-day business hours. The new profile persists in the existing workspace `settings_json.preferences`; the original timezone, language and date columns remain synchronized. Workspace creation can include the expanded settings. There is no destructive migration or new external service.

**Backward compatibility:** `services/preference_merge.py` merges only explicitly supplied PATCH fields, including nested day properties. An older client sending just timezone/language/date format cannot erase an extended profile or business hours. It revalidates the merged profile. A fragment that is valid alone but conflicts with persisted business hours returns HTTP **422** with a value-free message, not an unhandled validation error/HTTP 500. Invalid old stored values are displayed with safe defaults without silently mutating the database. Business hours are **reference data only**; this change does not enforce channel operating hours, automatically reply, or change conversation routing.

**Name validation:** `POST /api/v1/workspaces` and `PATCH /api/v1/workspace` retain their existing `name` length limits of 2–160 characters. A supplied name is now trimmed before persistence and rejected with HTTP **422** if fewer than two characters remain. `PATCH` still accepts an omitted or `null` name without replacing the existing value, and interior spacing remains unchanged. The General Settings form mirrors the requirement using a two-nonspace-character browser pattern; backend validation remains authoritative. Rejected requests must not alter preferences or emit general settings audit/outbox events.

The original Workspace page still renders the existing General Settings form, now delegated to `frontend/src/features/workspace/general/WorkspaceGeneralPanel.tsx` with the extended form in `WorkspaceGeneralDetails.tsx`. It continues to call `workspaceApi.update`. Users lacking `workspace.update` receive read-only controls while the backend remains the authorization authority. Existing IANA timezones and languages remain visible and editable using suggestion-backed inputs rather than being restricted to a short dropdown list; the workspace icon is displayed when no White Label logo exists. Workspace changes invalidate an in-flight form load/save display, and failed initial reads show an error and retry action. Existing team, developer, security, billing and White Label entries are preserved.

## Workspace ownership — new code, end-to-end acceptance pending

`GET /api/v1/workspace/owner` returns `ownerUserId`, `ownerName`, and `creatorUserId` for the **selected and authorized workspace**; owner and immutable creator are deliberately distinct. Existing workspace records with no stored `settings_json.ownerUserId` resolve a legacy owner from an active same-tenant workspace administrator, preferring `created_by` when still eligible. This fallback only reads; it does not silently rewrite old records. A workspace with no active admin reports a null owner and requires an independently authorized recovery process.

**Fail-closed recorded ownership:** once `ownerUserId` is explicitly saved by a transfer, the service does **not** fall back to the creator or any other administrator if that recorded owner is absent, inactive, not in this tenant, or no longer a workspace administrator. `GET` reports a null owner; `POST /owner/transfer` rejects with **409** and requires a separate audited, independently authorized recovery path. Invalid stored owner IDs likewise cannot confer ownership. The user-facing panel explains recovery without offering a misleading transfer form. No recovery endpoint or automatic takeover is implemented; the recovery design and verification remain an acceptance gap.

`POST /api/v1/workspace/owner/transfer` takes `{ "expectedOwnerUserId": "<UUID>", "targetUserId": "<UUID>", "confirmation": "TRANSFER", "reason": "administrative_handover" }`. Other allowed reason codes: `responsibility_change`, `account_recovery`. Requires the existing `members.manage` capability, an **interactive** session (not an API key), the **current owner's identity**, and a different **active administrator in this workspace and tenant**. A stale expected owner returns **409**. The workspace row is locked for transfer/member edits, and the owner, tenant/workspace-scoped `workspace.owner.transferred` audit and `workspace.owner.transferred.v1` outbox record are staged in the same transaction and committed once. The original `created_by` and both administrator roles remain unchanged. User IDs and reason code, not passwords or free-text secrets, enter the records. The existing member edit/remove service blocks changes to the effective owner with **409** until a transfer occurs. No schema migration, destructive data rewrite or external queue has been introduced.

Frontend: `WorkspaceOwnershipPanel.tsx` is a separate form under General Settings (never nested inside the profile form), uses the existing context-checked `workspaceApi` transport, shows a loading/error/retry state, offers only currently listed administrators, requires an explicit reason and typed `TRANSFER`, and invalidates stale workspace-selection displays. The server independently enforces every permission and membership check; hiding or disabling a frontend control is not authorization.

**Known limitations:** ownership currently lives in workspace settings JSON rather than a dedicated relational foreign key; independent platform account deactivation and owner recovery still require system-level design. Concurrent transfer/member enforcement relies on the workspace row lock on PostgreSQL and is **not verified by a production concurrency test**. API integration and frontend component tests are committed but **not verified as passing**.

## Checks before any merge

From `backend/`: `uv sync --all-groups --locked`, `uv run ruff check .`, `uv run ruff format --check .`, `uv run mypy src`, then run Workspace-focused unit/API tests including `tests/test_workspace_owner_unit.py`, `tests/test_workspace_owner_api.py`, `tests/test_workspace_owner_failclosed_api.py`, the General Settings/profile/preference/validation/access/transaction tests, `tests/test_workspace.py`, `tests/test_workspace_contract_unit.py`, `tests/test_workspace_api_keys.py`, and existing Workspace invitation/member tests. Run the complete backend suite and full frontend lint, typecheck, component tests (including `WorkspaceOwnershipPanel.test.tsx`), and build. Verify wrong-tenant and wrong-workspace access, API-key write rejection, current owner authorization, confirmation, stale expected owner, explicit ineligible-owner recovery denial, member-removal/demotion protection, transactional rollback, no secret leakage, and cross-workspace preference/ownership isolation. Check the **exact commit SHA** in CI and verify deployed behavior before merging.

**31 focused backend unit tests passed** in an isolated local environment using source/unit-test files whose Git blob hashes match GitHub (26 General Settings tests and 5 owner-selection tests); audit/outbox dependencies and database models were mocked for those tests. The latest ownership TSX passed **syntax-only** transpilation (zero diagnostics) against a hash-matched copy. These checks do **not** establish successful API/database integration, frontend component tests, full TypeScript typecheck, lint/format, full application suites, production concurrency or deployment. GitHub Actions has previously failed with inaccessible job steps/logs; the cause remains undiagnosed.
